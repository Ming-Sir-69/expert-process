# 流程卡、专家卡与偏好卡

## 模块接口

| 要素 | 约定 |
|---|---|
| 目标 | 把知识与偏好组织成可复用单元 |
| 输入 | 调研证据、用户原话、适用范围和来源 |
| 职责 | Agent整理；个人偏好由本人表述支持 |
| 处理 | 按实际用途整理process/expert/preference，核对来源、时间与适用条件 |
| 输出 | 任务所需卡片或可追溯来源；无需每条资料都建卡 |
| 验收 | 元数据合法，来源和适用条件明确，复用范围不被夸大 |
| 交接 | find供下次读取；integrate与gates只取当前适用内容 |

卡片是值得复用时采用的单元，写在档案的 `cards/` 下，复盘后用 `eca save` 入本工作区的库；入库不等于写入全局。一个流程一张卡，一个角色一张卡，偏好先按适用范围归属。用 `eca card <process|expert|preference> <id>` 按模板建。

- 流程卡、专家卡：行业知识，Agent 调研得来
- 默认围绕当前任务和项目保存，只有复用收益明确时才考虑额外提炼。
- scope描述适用范围，project与cross-project都可以保存为本地卡；跨项目标记不触发全局写入，也不指定存储服务。
- 卡片可以直接保存内容，也可用可选source_ref引用普通文件、URL或宿主已有来源。来源不可访问时如实说明，回到当前任务资料；只有确实缺少关键本人信息时才问，不要求为此接入某个系统。

## 共同的头部

```yaml
---
type: process            # process / expert / preference
id: brand-identity-design  # 小写字母、数字、连字符
title: 品牌标识设计流程
domain: 品牌设计
tags: [logo, 视觉识别]
updated: 2026-10-20
confidence: 中           # 高=多为 A/B 级且互相印证；中=有单一来源或推论；低=多为推论
---
```

`eca check` 会检查这几个字段是否齐全、type 与 id 是否合法。

## 流程卡正文

```markdown
## 适用范围
什么规模/行业/场景适用，不适用于什么。

## 阶段表
| 阶段 | 目的 | 产出 | 主导角色 | 协同/审批 | 关卡 | 没过关怎么办 |
|---|---|---|---|---|---|---|

## 常见变体与裁剪
小团队、低预算、个人项目时通常怎么简化。

## 来源
- [A/B/C] 标题 — 链接或出处（日期）
```

## 专家卡正文

```markdown
## 角色定位
在流程里负责什么，和谁交接。

## 考虑点（可检查）
- [ ] 每条都能判断做到/没做到，写清判断标准

## 知识储备
原则、标准、常用数值，每条注 [事实]/[推论] 和来源编号。

## 工具与方法
常用软件、模板、测试手段。

## 常见失误
外行最常犯、专家一眼挑出的问题。

## 流派分歧
不同观点各自是什么、各适合什么情况。

## 来源
- [A/B/C] 标题 — 链接或出处（日期）
```

## 偏好卡正文

```markdown
## 适用范围
谁、在什么类型的任务里。

## 偏好条目
| 条目 | 状态 | 日期 | 来源 |
|---|---|---|---|
| 报告先列结论 | 有效 | YYYY-MM-DD | 示例任务G1的用户原话 |

## 已推翻（留着，防止再犯）
| 旧条目 | 推翻于 | 改成 |
|---|---|---|

## 怎么问他最有效
交互方式上的偏好。
```

状态只用：有效 / 待确认 / 已推翻。`eca check` 会提醒超过 90 天还标"有效"的条目，建议在第一个关卡确认。

## 写卡原则

- 行业卡写清可复用的知识及其条件；用户偏好需要单独复用时整理为偏好卡，本次具体方案留在档案里。
- 能写成脚本判断的考虑点，在卡里写脚本名（如 `tools/colormetrics.py`）。
- 考虑点要具体到能打勾。"简洁"不合格；"在 16px 下仍能辨认主要形状"合格。
- 没查到的就不写，或写"未查到"。

## 经验与偏好的适用范围

下面是判断线索，不是逐项打分或固定晋级程序。Agent根据当前目标和上下文选择保留方式：

- **它依赖什么？** 某客户、数据结构、代码版本、预算、审批路径或当次偏好，通常属于任务/项目上下文。
- **去掉项目名称和业务细节还成立吗？** 如果结论随条件消失，就保留原情境；可以只提炼条件与反例，不抽象成普遍规则。
- **有多少独立使用证据？** 单次成功、一次审美选择或一个故障只是线索；多处重复成立更值得复用，但不设凑次数的门槛。
- **它是原则还是做法？** 稳定的判断原则可能复用；具体路径、参数、供应商限制和工具版本未必值得推广。
- **复用会带来收益还是污染？** 能节省重复判断、避免已证实错误才有价值；会误导其他项目、泄露上下文或增加维护负担时就留在原处。
- **本人明确说过适用范围吗？** 尊重当前用户和宿主已有的范围约定。一次方案选择不自动成为长期个人偏好；稳定个人偏好也不由某个项目规则擅自覆盖。

可选择留在任务日志/交付物、写成本项目卡片，或在有价值且符合已有授权时提炼为跨项目候选。无需每个任务都输出三份内容，也不把每条经验送入全局。范围暂不清楚时保留条件和未知，通常先留在项目内；只有判断差异会实质影响任务时才请用户澄清。

例如，某客户要求的报告字段通常留本项目；“空的工具回执不代表用户已回答”可以作为交互实现的复用候选；某次选定的标题、配色或部署参数保留在当次方案里。这里的例子只帮助理解，不替代模型判断。
