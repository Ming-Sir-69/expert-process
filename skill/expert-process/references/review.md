# 验收：用专家的眼睛检查

## 模块接口

| 要素 | 约定 |
|---|---|
| 目标 | 确认交付达到完成标准并标明证据边界 |
| 输入 | 实际交付、完成标准及相关依据；有必要时使用专家检查项 |
| 职责 | Agent检查可验证事项；用户给其专属验收判断 |
| 处理 | 分开结构、专业质量和本人认可，记录失败与未知 |
| 输出 | 逐项验收结论、证据和未覆盖项 |
| 验收 | 未检查不写通过；文件齐全不代替质量合格 |
| 交接 | 未通过则修正对应问题；有复用价值再交给retro |

目录：两层检查 → 逐条过检查项 → 风险门槛 → 什么时候停

## 1. 两层检查，不能互相顶替

| 层 | 查什么 | 怎么查 |
|---|---|---|
| 结构 | 实际产物的格式和规格是否达标（尺寸、格式、对比度、字段） | 用适用工具或脚本；`eca check`只管实际模式的档案和卡片结构 |
| 质量 | 是否达到专业水准、是否满足完成标准 | 取相关专业视角检查；不要求先建专家卡或遍历所有角色 |

结构全过 ≠ 质量合格。模型自评 ≠ 用户认可。

## 2. 选择相关检查项

检查服务本次完成条件，不因轻量省略必要检查，也不因全量额外凑检查数量。简单任务在交付中说明即可；全量档案写进`4_验收复盘.md`。

| 检查项 | 来自哪个专家 | 结果 | 依据 |
|---|---|---|---|
| 16px 下主要形状可辨认 | 标识设计师 | 通过 | 渲染 16px 截图对比 |

- 结果只用：**通过 / 不通过 / 未验证**。没有实际检查过的一律"未验证"，不写"应该没问题"。
- 能用工具判定的（尺寸、对比度、文件合法性），用工具判定并留下输出。
- 视觉产物必须按目标尺寸和场景实际渲染来看（截图、缩小、深浅底），只读源码不算验过。
- 对比度按**实际相邻的颜色**算：一个色块被另一个颜色框住时，它和框比，不是和底色比。算出来和目检不一致时先核对实际相邻色、输入与指标适用性，分开记录数值和目检；硬标准未达不能由目检直接改成通过。
- 有颜色承担区分作用时，做**红绿色弱模拟**（`tools/colormetrics.py`），并在小尺寸下看一遍。
- 专业审美与品牌契合度可由Agent判断并说明理由；只有需要本人偏好、验收意见或约定的签核时才问。未经本人评价不能声称“用户已认可”，也不因尚无反馈否定已有客观检查。
- 不通过的项：能改就改完再验一次；改不了的写清原因和影响。

## 3. 风险门槛

- 低风险、可逆：带着明确标注的推论交付，待验证项列出来即可。
- 中风险或对外交付：关键说法至少交叉核对一次或实测一次；未证实的内容单独隔开。
- 高风险动作：补足相关关键依据，并核对已有授权与恢复条件；缺少无法替代的证据就说明限制，不让用户选择替代专业事实判断。只暂停无法推进的部分，不自动增加无关阶段。

## 4. 什么时候停

完成标准都满足、检查项都有结论，就交付。不追加用户没要的版本、文档或测试。没满足的标准如实说明，不硬凑。
