# 调研：流程与专家怎么查

## 模块接口

| 要素 | 约定 |
|---|---|
| 目标 | 获得本任务适用的行业流程和专家依据 |
| 输入 | 当前问题、已有资料与影响结果的知识缺口 |
| 职责 | Agent调研和核对；用户提供自有资料 |
| 处理 | 按问题查原始来源，验证算/查约束与适用范围 |
| 输出 | 适用依据、来源和未知项；有复用价值时整理卡片 |
| 验收 | 关键问题有依据，来源支持所作判断，未知不冒充事实 |
| 交接 | 当前方案使用依据；确需复用时由cards组织 |

目录：要回答的问题 → 去哪找 → 查询写法 → 来源分级 → 何时停 → 常见陷阱

仅在知识缺口影响当前判断时调研，查对应问题，不默认研究整个行业。结果可直接用于当前方案并附来源；有续接或复用价值时才写记录或卡片（见cards.md）。以下问题按需选择，不是逐项完成清单。

## 1. 要回答的问题

**流程调研**（需要组织多个阶段时）
1. 这个行业/场景的成熟做法分几个阶段？每阶段的目的是什么？
2. 每阶段**产出什么**（文档、物件、决定）？下一阶段拿它做什么？
3. 每阶段**谁参与**（角色/部门），谁主导、谁审批、谁交接给谁？
4. 阶段之间的**关卡**是什么（评审、签核、测试、客户确认）？没过关怎么回退？
5. 有哪些常见变体（规模、预算、行业细分），本任务该怎么裁剪？

**专家调研**（缺少相关专业视角时，不要求每个角色建卡）
1. 这个角色在本类任务里**关注什么**？写成能逐条打勾的考虑点。
2. 他们靠什么**知识**判断：原则、标准、常用数值和阈值、术语。
3. 用什么**工具/方法**：软件、模板、测试手段、评审表。
4. 新手和外行最常犯什么**错**？专家一眼会挑出什么毛病？
5. 不同流派之间有什么**分歧**？

**约束核对**（在提出受这些约束影响的选项前）
1. 这个决定有没有**能计算或有硬标准**的约束？（无障碍、色弱、对比度、尺寸、技术限制、预算、法规）
2. 有没有**混淆或冲突**风险？（如与现有接口、竞品、用户点名要避开的对象冲突；仅核对相关部分）
3. 有没有适用于本情境的研究或实践依据？说明证据能支持到哪里，不将单个小实验、科普转述或一个案例夸大为行业定律。

先筛掉不可用的选项，再在确需本人信息时提问（见gates.md）。已有确定性脚本可直接使用；本次临时检查脚本留在项目或外部运行区，不因一次调研修改工具源码。

## 2. 去哪找

按任务情境选，下面不是固定顺序：

- **规范层**：国际/国家标准、行业协会指南、监管文件、平台官方规范（如应用商店、开源平台的图像规格）。
- **方法层**：头部机构公开的工作方法、知名事务所/工作室的流程说明、专业教材与课程大纲、资深从业者的系统性文章或演讲。
- **实践层**：案例复盘、项目过程记录、作品集里的"过程"页、评审意见、职位描述（JD 里的职责和技能要求是专家考虑点的好来源）。
- **反面层**：失败案例、常见错误清单、专业评论里的批评。
- **用户自有资料**：用户给的文件、过往决定和偏好，说明其来源和适用范围；当前明确要求优先，但偏好不能替代客观标准或事实证据。
- 资料形态不限：网页、PDF、代码与测试、视频字幕都能当证据，抓取到的原文保存要点和出处即可。
- **参考作品板**（设计、文案、方案类任务）：它主要用来帮用户说出喜好，当作关卡工具用，写法见 gates.md。用户要求过“参考现成设计”时不能省。

## 3. 查询写法

- 流程：`<领域> process stages deliverables`、`<领域> workflow phases`、`<领域> 流程 阶段 交付物`、`<领域> agency process`、`<领域> SOP`。
- 角色：`<角色> checklist`、`<角色> responsibilities`、`<角色> common mistakes`、`what <角色> look for in <对象>`、`<角色> 评审 要点`。
- 标准与数值：`<对象> guidelines minimum size`、`<对象> specification`、`<平台> requirements`。
- 查询围绕未解决的问题收窄，语言贴近原始资料；仅在有帮助时换措辞、语言或来源类型，不机械凑查询次数。
- 搜索摘要不够时，打开原文读；同一结论追到最早的出处，转载不算独立来源。

## 4. 来源分级（按情境判断，不机械排序）

| 级 | 类型 | 用法 |
|---|---|---|
| A | 标准、法规、官方规范、协会正式指南 | 可直接作 [事实]，注明版本/日期和适用范围 |
| B | 头部机构方法、教材、资深从业者系统论述 | 可作 [事实]，注明是谁的方法；不同流派分开记 |
| C | 案例、社区讨论、博客 | 可支持该来源的观察；推广为一般结论须有适用性依据，多个转述不算独立印证 |
| D | 模型自己的推导 | 只能是 [推论] 或 [假设] |

冲突时看三件事：谁更权威、谁更新、谁更贴近本任务的情境（地区、规模、平台）。处理方法见 integrate.md。

## 5. 何时停

- 按关键问题的覆盖、来源支持力度和风险判断是否足够；重要事实优先追到可复核的原始依据，不按固定数量凑来源；
- 继续查找已难以改变当前判断时，说明仍未知的部分及影响，决定能否在这些边界内推进；
- 单一来源如足够支持当前说法可以使用，重要限制在交付或已有记录中说明，不为此单独建档。

不要为了凑来源无限搜。查不到的付费标准、书籍正文如实标"未查到"。

## 6. 常见陷阱

- 把一个工作室的流程当成行业通则——注明来源是谁的方法。
- 专家考虑点写成空话（"要有美感""注意用户体验"）——每条必须能判定是否做到。
- 用模型记忆补数值或标准号——没查到就别写。
- 只查"怎么做"不查"常见错误"——专家价值常在挑错。
