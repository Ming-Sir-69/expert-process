# Expert Process

**分工**：Agent 用流程做行业适配，给出专业场景下的方案；人提供视角和偏好，决定"是不是他想要的"。两边的知识都靠积累：行业知识沉淀成**流程卡、专家卡**，经验和偏好先保留在适合本任务、项目的位置；有跨项目价值时再按宿主已有约定考虑提炼。使用前核对来源、时间与适用范围，本工具不绑定外部记忆服务。

## 核心：按不确定性分流

每个会影响结果的决定，登记进作战图的"决策登记"，先分类再动手：

| 类型 | 是什么 | 谁解 | 怎么解 |
|---|---|---|---|
| **算** | 可计算、有硬标准（对比度、色弱、尺寸、格式、预算上限） | Agent | 脚本检查，过不了就改；不问人 |
| **查** | 行业惯例（交付物清单、阶段、规范） | Agent | 调研 → 卡片；写明依据，不问人 |
| **问** | 偏好、品味、取舍、只有用户知道的情境 | 人 | 关卡：先准备好选项再问 |
| **确认** | 不可逆、花钱、对外发布、删改他人文件 | 人 | 停下，一句话确认 |

两条顺序规则：

1. **先算、查，再问**。给用户的选项先过"算""查"两道筛，风险标在选项上。不要让用户在不可用的选项里挑
2. **先问上游，再问下游**：方向 → 结构 → 颜色 / 语气 → 细节。上游变化时重审依赖它的下游，保留未受影响的结果

分不清是"查"还是"问"时，看行业有没有共识：有共识就查，没有共识或因人而异就问。

## 档位

| 档位 | 何时 | 做法 |
|---|---|---|
| 轻 | 小、可逆、低风险 | 不建档案；决策分流和关键来源写在回复里 |
| 标准 | 正式交付物、多阶段或多角色 | 建档案，走全程 |
| 深 | 对外发布、花钱、不可逆、合规，或来源冲突多 | 标准 + 多源交叉核对 + 关键假设做最小验证 |

拿不准选标准。"问"类决定多就多设关卡；"查"类不确定多就调研深一些。

## 档案就是记忆

能执行命令时，在本工具包的根目录运行以下命令；中间结果从第一版起写进档案，不只留在对话或临时目录里：

```
python3 cli/eca.py new <slug> --title "任务名"   # 建档案：1_简报 2_作战图 3_日志 4_验收复盘
python3 cli/eca.py find <关键词>                 # 查流程卡、专家卡、偏好卡
python3 cli/eca.py gate <run> --id G1 ...        # 记一条关卡（见 gates.md）
python3 cli/eca.py status [run]                 # 进度；不带参数看最近改过的档案
python3 cli/eca.py check [run]                  # 结构检查 + 漏问、漏回写提醒
python3 cli/eca.py save <run>                   # 卡片入库
python3 cli/eca.py stats                        # 各档案关卡数、改变方向的次数
```

CLI、模板与tools属于完整工具包，Skill ZIP不包含它们。命令相对于工具包根目录执行，数据保存在该目录的runs/与library/；单独安装Skill时仍需保留完整工具包才能调用CLI。无命令能力时按单文件方式记录，不假装已运行CLI。

四个文件都是**活文档**：关卡先登记事前方案，实际答复后追加结果并回写简报和作战图，不等到最后补。中断后先 `status`，读档案续做。不能执行命令时（ChatGPT Library、Claude 项目文档），方法照做，四个文件以小节形式写在回复或项目文档里。

## 统一接口

模块和阶段共用目标、输入、职责、处理、输出、验收、交接七项；状态与裁剪理由随任务维护，见[接口与交接约定](references/workflow.md)。

## 流程

1. **简报** → `1_简报.md`：目标、交付物、完成标准、档位。先 `find`：读取当前请求、项目记录和可访问的相关资料；对影响任务的过期/冲突条目提问，已有明确答案不重复问。
2. **调研** → `cards/`：流程（阶段、产出、协同、关卡）和关键角色（考虑点、知识、工具、常见失误）直接写成卡片；库里有就复用，按 [retro.md](references/retro.md) 判断时效。方法见 [research.md](references/research.md)，卡片格式见 [cards.md](references/cards.md)。
3. **作战图** → `2_作战图.md`：一张实际任务的阶段表，记录需要的专家职责、检查项、处理方式和交接；另有**决策登记**（类型、次序、依据）。见 [integrate.md](references/integrate.md)。
4. **执行与关卡** → `3_日志.md` + `outputs/`：按阶段产出，过程稿和生成脚本放 `outputs/drafts/`。能脚本化的检查用脚本（`tools/`）。到"问"类决定就开关卡，规则见 [gates.md](references/gates.md)。偏离作战图要在日志里写原因。
5. **验收与复盘** → `4_验收复盘.md`：逐条过完成标准和检查项，分清已验证和未验证（见 [review.md](references/review.md)）；复盘"问"了哪些、哪些真的改变了方向；值得复用的卡片用 `save` 入库，新信息按范围回写任务/项目记录（见 [retro.md](references/retro.md)）。

## 证据规则（全程）

- 关键说法标 **[事实]**（附来源）、**[推论]**（写前提）、**[假设]**（写怎么验证）。
- 不编造来源、数字、标准号、引用、作品；查不到就写"未查到"。
- 模型自信、文笔流畅、来源数量都不是证据。来源分级见 research.md。
- 用户的偏好也要有出处：哪次说的、原话是什么。模型的推测不能写成用户偏好。

## 经验与偏好的范围

用户当前明确要求和适用的项目约定优先。一次任务的选择、局部约束和单个反例先留在本项目；是否可抽象为跨项目经验，由Agent判断。可以考虑它依赖哪些条件、在别处是否重复成立、去掉业务细节后是否仍有用，以及共享后会不会误导其他任务。具体思路见[cards.md](references/cards.md)，不要求每条内容都入库或上升为通用规则。真正影响结果的偏好冲突通过关卡澄清。

## 停止与升级

- 尚未被当前或既有授权覆盖的确认类动作等待本人；常规范围内可逆工作直接推进，优先使用已有版本历史或工具回退。涉及唯一原件或不可恢复数据时先处理恢复路径；若仍不可逆，按用户授权边界处理，不把每次普通修改都变成快照流程。
- 缺工具就说缺什么，不假装执行过。
- 达到完成标准就停，不追加没被要求的产物和验证。

## 固化成独立技能（条件）

同类任务反复出现、卡片已稳定时，才考虑把卡片打包成独立 Skill，见 [forge.md](references/forge.md)。不为一次性任务造技能。
